## 1. 왜 지금 결제를 붙일 수 없는가

PG사 가입 심사에는 다음이 필요합니다.

- 사업자등록증
- 통신판매업 신고증
- 사업용 통장 사본
- 대표자 신분증
- **심사 통과 가능한 웹사이트** — 요금제 페이지, 이용약관, 환불규정, 사업자정보 표기

앞의 넷은 사업자등록 이후에나 생깁니다. **다섯 번째는 이번 작업으로 이미 갖췄습니다.**
`index.html` 하단 `BIZ_INFO` 의 `○○` 값만 실제 정보로 채우면 심사에 제출할 수 있는 상태가 됩니다.

```js
// index.html
const BIZ_INFO = {
  company:  'INTO OFFICE',
  ceo:      '○○○',                 // ← 대표자 성명
  bizNo:    '○○○-○○-○○○○○',        // ← 사업자등록번호
  mailNo:   '제0000-○○○○-0000호',   // ← 통신판매업 신고번호
  address:  '○○시 ○○구 ○○로 ○○',
  tel:      '○○-○○○○-○○○○',
  email:    '○○○@○○○'
};
```

## 2. PG사 선택

| | 토스페이먼츠 (직계약) | 포트원 (구 아임포트) |
|---|---|---|
| 구조 | PG와 직접 계약 | 여러 PG를 하나의 API로 통합 |
| 수수료 | 상대적으로 유리 | PG 수수료 + 중개 |
| PG 교체 | 재개발 필요 | 설정 변경만 |
| 문서 품질 | 매우 좋음 | 좋음 |
| **권장** | 카드 결제만 단순하게 갈 때 | **초기 스타트업 — 이쪽 권장** |

**포트원을 권합니다.** 초기에는 어떤 PG의 심사가 언제 통과할지 알 수 없고, 수수료 협상력도 없습니다.
포트원을 쓰면 PG가 바뀌어도 우리 코드는 그대로입니다.

## 3. 정기결제(빌링) 동작 원리

구독 서비스이므로 **일반 결제가 아니라 빌링키 결제**를 써야 합니다.

```
[최초 1회]
  고객 → 카드 등록창 (PG가 제공)
       → PG가 카드정보를 보관하고 "빌링키" 발급
       → 우리 서버는 빌링키만 저장   ← 카드번호·CVC는 절대 받지 않음

[매월 결제일]
  우리 서버 → PG에 "이 빌링키로 19,900원 청구해줘"
           → 결제 성공/실패 응답
           → billing.payments 에 기록, 구독 기간 연장
```

### 🔴 절대 하지 말 것

- **카드번호·유효기간·CVC를 우리 DB에 저장** — 위법이자 사고의 지름길입니다
- **빌링키를 클라이언트에 노출** — 빌링키만 있으면 고객 개입 없이 계속 결제됩니다
- **빌링키 발급 전 본인인증 생략** — 타인 카드 등록 악용 경로가 됩니다

> 마이그레이션의 `esign_my_subscription()` 은 빌링키를 절대 반환하지 않고
> `has_billing_key: true/false` 만 내려주도록 이미 설계되어 있습니다.

## 4. 구현 순서

### 4-1. DB 마이그레이션 적용

```bash
supabase db push
# 또는 Supabase 대시보드 SQL Editor 에 붙여넣기
```

적용해도 **동작은 전혀 바뀌지 않습니다.** `billing.settings.enforce_quota` 가 `false` 이기 때문입니다.

확인:

```sql
select * from billing.settings;          -- enforce_quota = false
select public.esign_list_plans();        -- 4개 플랜 반환
```

### 4-2. 프론트에 사용량 표시 (결제 없이 먼저 가능)

대시보드에 이번 달 사용량을 노출합니다. 결제 붙이기 전에 해두면
**고객이 한도 개념에 미리 익숙해져서** 나중에 과금 전환이 부드럽습니다.

```js
const { data } = await sb.rpc('esign_my_subscription');
// data.plan.name          → '무료'
// data.usage.used         → 2
// data.usage.limit        → 3   (null 이면 무제한)
// data.usage.remaining    → 1
// data.usage.exceeded     → false
```

문서 생성 화면 진입 시 사전 확인:

```js
const { data } = await sb.rpc('esign_check_quota');
if (data.ok && !data.allowed) {
  showToast(data.message);   // "무료 요금제의 이번 달 발송 한도(3건)를 …"
  openPricing();
  return;
}
```

### 4-3. Edge Function 3종 (사업자등록 후)

기존 `esign-sign` Edge Function과 같은 구조로 추가합니다.
**PG 시크릿 키는 반드시 Edge Function 환경변수**에 두고, 프론트에는 절대 넣지 않습니다.

| 함수 | 역할 |
|---|---|
| `billing-issue-key` | 빌링키 발급 요청 처리 → `billing.subscriptions.billing_key_ref` 저장 |
| `billing-charge` | 빌링키로 실제 청구 → `billing.payments` 기록 → 구독 기간 연장 |
| `billing-webhook` | PG 웹훅 수신 (결제 성공/실패/취소 통보) |

### 4-4. 매일 도는 정기결제 배치

Supabase의 `pg_cron` 으로 매일 결제 대상을 찾아 `billing-charge` 를 호출합니다.

```sql
-- 오늘 결제해야 할 구독
select id, owner_id, plan_code, billing_cycle
  from billing.subscriptions
 where status in ('active','past_due')
   and cancel_at_period_end = false
   and billing_key_ref is not null
   and current_period_end <= now();
```

**결제 실패 처리 정책** (약관 제8조와 일치시킬 것):

| 시점 | 조치 |
|---|---|
| 실패 즉시 | `status = 'past_due'`, 고객에게 알림. 서비스는 계속 이용 가능 |
| +3일 | 재시도 |
| +7일 | 재시도 + 이용 제한 예고 |
| +14일 | `status = 'canceled'`, 무료 요금제로 강등 |

> 결제 실패 즉시 서비스를 끊으면 안 됩니다. 카드 갱신 지연은 흔한 일이고,
> 계약서를 맡겨둔 고객이 갑자기 문서에 접근하지 못하면 그 자체가 사고입니다.

### 4-5. 멱등성 — 이게 결제에서 제일 중요합니다

PG 웹훅은 **같은 이벤트를 여러 번 보냅니다.** 배치도 재시도로 중복 실행될 수 있습니다.
그래서 `billing.payments.pg_order_id` 에 **unique 제약**을 걸어 두었습니다.

```sql
insert into billing.payments (owner_id, plan_code, amount, vat, pg_order_id, ...)
values (...)
on conflict (pg_order_id) do nothing;   -- 중복 청구 방지
```

주문번호는 **결제 주기당 하나로 결정적으로** 만드세요. 무작위 값을 쓰면 멱등성이 깨집니다.

```
order_id = "sub_{subscription_id}_{YYYYMM}"
```

### 4-6. 한도 강제 켜기

결제가 실제로 돌기 시작한 뒤에 켭니다.

```sql
-- 켜기 전 확인: 이미 한도를 넘긴 고객이 있는지
select p.email,
       (billing.effective_plan(p.user_id)).code  as plan,
       billing.docs_used(p.user_id)              as used,
       (billing.effective_plan(p.user_id)).monthly_doc_limit as lim
  from esign.profiles p
 where p.status = 'active';

-- 켜기
update billing.settings set enforce_quota = true, updated_at = now() where id;

-- 되돌리기
update billing.settings set enforce_quota = false, updated_at = now() where id;
```

한도를 초과한 상태에서 `esign.documents` INSERT 를 시도하면 트리거가 다음 오류를 냅니다.

```
QUOTA_EXCEEDED: 무료 요금제의 이번 달 발송 한도(3건)를 모두 사용했습니다.
```

프론트에서 이 문자열을 잡아 요금제 안내로 유도하세요.

```js
if (String(error?.message || '').includes('QUOTA_EXCEEDED')) {
  showToast('이번 달 발송 한도를 모두 사용하셨습니다.');
  openPricing();
}
```

### 4-7. 세금계산서

B2B 고객은 매월 세금계산서를 요구합니다. 고객이 10곳만 넘어도 수동 발행은 무너집니다.

- 팝빌 / 바로빌 등 전자세금계산서 API 연동
- `billing.payments.status = 'paid'` 기록 시 자동 발행
- 발행에 필요한 정보(사업자등록번호, 상호, 대표자, 업태·종목, 담당자 이메일)를
  **구독 신청 단계에서 미리 받아두세요.** 나중에 다시 물어보면 응답률이 떨어집니다.

## 5. 검증 체크리스트

DB 스키마는 임시 PostgreSQL 16 인스턴스에서 실제로 적용·실행해 다음을 확인했습니다.

- [x] 마이그레이션이 오류 없이 적용됨
- [x] `esign_list_plans()` 가 4개 플랜 반환
- [x] 구독 행이 없는 이용자는 자동으로 `free` 요금제로 간주됨
- [x] `enforce_quota = false` 인 동안에는 한도를 넘겨도 차단되지 않음 (기존 이용자 무영향)
- [x] `esign_check_quota()` 가 초과 시 한국어 안내 문구 반환
- [x] `enforce_quota = true` 로 켜면 한도 초과 INSERT 가 차단됨
- [x] 상위 요금제로 변경하면 즉시 발송 재개
- [x] 무제한 요금제(`monthly_doc_limit is null`)는 차단되지 않음
- [x] `esign_my_subscription()` 응답에 빌링키가 포함되지 않음

결제 연동 후 반드시 추가로 확인할 것:

- [ ] 웹훅 중복 수신 시 이중 청구가 발생하지 않는가 (같은 `pg_order_id` 로 두 번 호출해볼 것)
- [ ] 결제 실패 시 서비스가 즉시 끊기지 않는가
- [ ] 요금제 변경 시 일할 정산이 약관 제8조와 일치하는가
- [ ] 해지 후 문서 다운로드 유예기간(약관상 30일)이 실제로 동작하는가
- [ ] 빌링키가 클라이언트 응답·로그·에러 메시지 어디에도 찍히지 않는가

## 6. 순서 요약

```
사업자등록증 발급
   ↓ (당일)
PG 가입 신청  ─────────────── 심사 2~4주 (최장 병목)
   ↓
구매안전서비스 이용확인증 발급
   ↓
통신판매업 신고 → 신고번호를 BIZ_INFO 에 반영
   ↓
PG 심사 완료 · 상점 키 발급
   ↓
Edge Function 3종 구현 → 테스트 결제
   ↓
정기결제 배치 (pg_cron) 가동
   ↓
enforce_quota = true
   ↓
유료 오픈
```

**심사 대기 2~4주 동안 놀지 마세요.** 그 기간에 할 수 있는 일:

- 사용량 표시 UI (4-2) — 결제 없이 지금 가능
- 공개 랜딩페이지 제작
- 약관·처리방침 변호사 검토
- Supabase RLS 전수 점검 (로드맵 4단계 참고 — **오픈 전 필수**)
- 인투유학 1호 고객 온보딩
