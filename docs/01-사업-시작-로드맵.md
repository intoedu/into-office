## 1단계 — 사업 형태 결정 (D+0 ~ D+7)

### 개인사업자 vs 법인

| | 개인사업자 | 법인(주식회사) |
|---|---|---|
| 설립 비용 | 0원 | 등록면허세 + 법무사 수수료 (대략 30~80만원) |
| 설립 기간 | 즉시~3일 | 1~2주 |
| 세율 | 종합소득세 6~45% 누진 | 법인세 9~24% |
| 대외 신뢰도 | 낮음 (대기업·공공 납품 시 불리) | 높음 |
| 투자 유치 | 사실상 불가 | 가능 |
| 정부지원사업 | 일부 가능 | 대부분 가능 |
| 대표 책임 | 무한책임 | 유한책임 |
| 이익 인출 | 자유 | 급여/배당 절차 필요 |

### 권장

**법인 설립을 권합니다.** 이유:

1. **B2B SaaS**라서 고객사가 사업자등록증·법인등기부를 요구하는 경우가 잦습니다. 특히 개인정보를 다루는 전자계약은 고객사 보안 심사를 통과해야 합니다.
2. 전자서명은 **신뢰 산업**입니다. 계약서를 맡기는 서비스인데 개인사업자면 도입 검토 단계에서 탈락합니다.
3. 향후 KISA 평가·인정, 정부지원사업, 투자 유치까지 갈 여지가 큽니다.

단, 매출이 완전히 불확실하고 첫 1년 매출이 3천만원 미만으로 예상된다면 **개인사업자로 시작 → 매출 발생 후 법인전환**도 현실적입니다. (법인전환 시 사업양수도 절차 필요, 비용 발생)

### ⚠️ 자본금 설정 시 반드시 확인

법인 설립 시 **자본금을 1억원 이하로 설정**하세요.

- 전기통신사업법상 **부가통신사업 신고**는 자본금 1억원 이하이면 **면제**됩니다.
- 자본금이 1억원을 초과하면 초과일로부터 **1개월 이내**에 과학기술정보통신부에 부가통신사업 신고를 해야 합니다.
- 초기에는 자본금 1,000만원~5,000만원 수준이면 충분합니다. 필요 시 나중에 증자하면 됩니다.

- [ ] (법인 시) 상호·본점 소재지·자본금·주주구성 확정

## 3단계 — 온라인 사업 인허가 (D+14 ~ D+21)

### 3-1. 통신판매업 신고 — **필수**

유료 구독 결제를 받는 순간 대상입니다.

- 신청처: 관할 **시·군·구청** 또는 정부24
- 비용: **등록면허세 연 1.8만~4.05만원** (지자체 인구 규모별 차등, 매년 1월 납부)
- **선행 조건: 구매안전서비스 이용확인증(에스크로)** — PG사 또는 은행에서 발급받습니다.
  → 즉 **PG 계약이 통신판매업 신고보다 먼저**입니다. (5단계 참조)

### 3-2. 부가통신사업 신고 — **자본금 1억 이하면 면제**

- 자본금 1억원 초과 시에만 신고 의무
- 1단계에서 자본금을 1억 이하로 설정했다면 지금은 넘어가도 됩니다
- 향후 증자로 1억을 넘기면 **1개월 이내** 신고

### 3-3. 정보통신망법상 의무

- 이용약관 게시
- 개인정보처리방침 **상시 공개** (홈페이지 첫 화면에서 접근 가능해야 함)
- 개인정보보호책임자(CPO) 지정 및 성명·연락처 공개

## 4단계 — 법무·컴플라이언스 (D+14 ~ D+35) ★ 가장 중요

### 4-1. 전자서명법 — 인허가는 필요 없습니다

| 질문 | 답 |
|---|---|
| 전자서명 서비스를 하려면 정부 허가가 필요한가? | **아니오.** 별도 인허가 없이 사업 가능합니다. |
| KISA "전자서명인증사업자 운영기준 준수사실 인정"은? | **임의(자율) 제도**입니다. 필수가 아닙니다. |
| 그럼 왜 받나? | 대외 신뢰도 + **공공·금융 고객 영업 시 사실상 전제조건**이 될 수 있습니다. |
| 유효기간 | **1년** (매년 갱신 평가 필요) |

> 2020년 전자서명법 전면 개정으로 공인인증서 독점이 폐지되면서, 사설 전자서명 서비스가 자유롭게 진입할 수 있게 되었습니다.
> **초기에는 인정 없이 시작하고**, 유료 고객이 붙고 공공·금융 영업을 시작할 때 평가·인정을 검토하는 것이 순서입니다.
> 참고: [KISA 전자서명인증사업자 인정·평가 제도](https://www.kisa.or.kr/1050609)

### 4-2. 전자문서법 — 여기가 제품 경쟁력입니다

전자문서 및 전자거래 기본법상 전자문서는 문서로서 **법적 효력이 인정**됩니다.
분쟁이 났을 때 실제로 다투는 지점은 "전자문서가 유효한가"가 아니라 **"이 서명을 정말 그 사람이 했는가"**입니다.

즉 **감사추적(audit trail)이 곧 증거력**이고, 곧 상품성입니다.

지금 `audit_logs` 테이블과 `esign_get_audit_cert` RPC가 이미 있습니다. 다음 항목이 다 기록되는지 점검하세요:

- [ ] 서명자 신원확인 수단 (이메일 / 휴대폰 인증 / 카카오)
- [ ] 접속 IP 주소
- [ ] User-Agent (기기·브라우저)
- [ ] 각 이벤트의 타임스탬프 (열람 / 서명 시작 / 서명 완료 / 다운로드)
- [ ] **원본 문서 해시값** (`documents.file_hash` 컬럼 존재 — 실제 채워지는지 확인)
- [ ] 서명 완료본 해시값
- [ ] 서명 이미지 좌표·페이지

> **추천 개선**: 완료 PDF 마지막 장에 감사추적 인증서를 자동 첨부하고, 문서 해시를 함께 인쇄하세요.
> 경쟁사가 다 하는 기능이고, 없으면 B2B 검토 단계에서 지적당합니다.

**타임스탬프(TSA)**: 공인 시각인증은 초기엔 없어도 되지만, 대기업·공공 영업 시 요구될 수 있습니다. 로드맵 후반 과제로 남겨두세요.

### 4-3. 개인정보보호법 — 과태료 리스크 1순위

전자계약 서비스는 **남의 계약서**를 보관합니다. 개인정보 취급 강도가 매우 높습니다.

**수집·처리하는 개인정보 목록** (처리방침에 그대로 들어가야 함):

| 대상 | 항목 |
|---|---|
| 회원(발송자) | 이메일, 아이디, 이름, 휴대폰번호, 소속/상호, 사업자유형, 생년 |
| 서명자(비회원) | 이름, 이메일 또는 휴대폰번호, **서명 이미지**, 접속 IP, 기기정보 |
| 문서 | 업로드한 PDF 내용 전체 (제3자 개인정보가 포함될 수 있음) |

**⚠️ 특히 주의할 점**

1. **서명 이미지는 민감하게 취급하세요.** 법적으로 생체정보로 분류되지는 않지만, 필체는 위조에 악용될 수 있습니다. 접근 통제와 암호화가 필요합니다.
2. **문서 내용에 대한 처리자 지위**: 고객사가 업로드한 계약서 속 개인정보에 대해 INTO OFFICE는 **수탁자(처리위탁받은 자)**입니다. → B2B 고객과 **개인정보 처리위탁 계약서**를 별도로 체결해야 합니다.
3. **보유기간**: 완료된 계약서를 언제까지 보관할지 정하고 명시해야 합니다. (예: 회원 탈퇴 후 즉시 파기 / 계약서는 5년 등) 무기한 보관은 위법 소지가 있습니다.

**국외이전 이슈**

- Supabase 프로젝트는 **ap-northeast-2 (서울)** 리전이라 데이터 자체는 국내에 저장됩니다. — 유리한 조건입니다.
- 다만 Supabase Inc.는 해외 법인이며 운영·기술지원 과정에서 접근 가능성이 있으므로, **개인정보처리방침의 '처리위탁' 및 '국외이전' 항목에 기재**해 두는 것이 안전합니다.
- 계약의 체결·이행에 필요한 범위라면 **별도 동의 없이 개인정보처리방침 공개로 갈음**할 수 있습니다. (개인정보보호법 제28조의8)

- [ ] 개인정보처리방침 확정 (변호사 검토)
- [ ] 개인정보보호책임자(CPO) 지정
- [ ] 감사추적 기록 항목 점검 및 보완
- [ ] 완료 PDF에 감사추적 인증서 자동 첨부
- [ ] **Supabase RLS(Row Level Security) 전수 점검** — 아래 참조

### 🔴 보안 긴급 점검 항목

`index.html`에 Supabase publishable key(`sb_publishable_...`)와 카카오 JS 키가 그대로 들어있습니다.
**이 자체는 정상입니다** (공개용 키). 다만 전제 조건이 있습니다:

- [ ] `esign` 스키마 모든 테이블에 **RLS 활성화 + 정책 검증**. RLS가 뚫려 있으면 publishable key만으로 **남의 계약서를 전부 읽을 수 있습니다.**
- [ ] Storage 버킷 `esign-docs` 접근 정책 점검. 코드에 `getPublicUrl()` 호출이 있는데, 버킷이 public이면 **URL만 알면 누구나 계약서를 받습니다.** → 서명용 URL(signed URL)로 전환 검토
- [ ] 카카오 개발자 콘솔에서 **플랫폼 도메인 제한** 설정
- [ ] `esign_*` RPC 함수의 권한 검증 로직 점검 (특히 `esign_set_member_role`, `esign_delete_member` 등 관리자 함수)

> 이건 사업 개시 전 필수입니다. 전자계약 서비스에서 문서 유출 사고가 나면 사업이 끝납니다.

## 5단계 — 결제 인프라 (D+21 ~ D+50)

### PG사 선택

| | 토스페이먼츠 (직계약) | 포트원 (구 아임포트) |
|---|---|---|
| 방식 | PG사와 직접 계약 | 여러 PG를 하나의 API로 통합 |
| 장점 | 수수료 유리, 문서 깔끔 | 연동 1회로 PG 교체 자유, 개발 빠름 |
| 단점 | PG 바꾸려면 재개발 | 중개 레이어 추가 |
| 추천 | 결제 수단이 카드 위주로 단순할 때 | **초기 스타트업 권장** |

**정기결제(빌링키) 필수**입니다. 구독 서비스이므로:

1. 고객이 최초 1회 카드 등록 → PG가 **빌링키** 발급 (카드번호는 우리 서버에 저장하지 않음)
2. 매월 결제일에 빌링키로 자동 청구
3. 빌링키는 한 번 발급되면 고객 개입 없이 계속 결제되므로, **발급 시 본인인증을 반드시 선행**해야 합니다

> 카드번호·CVC를 **절대 자체 DB에 저장하지 마세요.** 빌링키만 저장합니다.

### PG 계약 준비물 & 소요 기간

- 사업자등록증
- 통신판매업 신고증 (또는 신고 예정 확인)
- 대표자 신분증
- 사업용 통장 사본
- 홈페이지 URL (**심사 대상**: 요금제 페이지, 이용약관, 환불규정, 사업자정보 표기가 다 있어야 통과)
- **심사 기간 2~4주** → 사업자등록 나오는 즉시 신청하세요. 여기가 최장 병목입니다.

> ⚠️ **순환 의존성 주의**
> 통신판매업 신고에는 PG의 구매안전서비스 확인증이 필요하고, PG 심사에는 통신판매업 신고증이 필요한 경우가 있습니다.
> 실무 순서: **PG 가입 신청 → 구매안전서비스 확인증 발급 → 통신판매업 신고 → 신고증 제출로 PG 심사 완료**
> 신청 시 PG사 담당자에게 "통신판매업 신고 전"이라고 미리 알리면 순서를 잡아줍니다.

### 세금계산서

B2B는 매월 세금계산서를 요구합니다. 수동 발행은 고객 10곳만 넘어도 무너집니다.

- 팝빌, 바로빌 등 전자세금계산서 API 연동 (건당 수십원 수준)
- 결제 성공 → 세금계산서 자동발행 파이프라인 구성

### 체크리스트

- [ ] PG사 선정 (포트원 권장)
- [ ] PG 가입 신청 및 심사 서류 제출
- [ ] 구매안전서비스 이용확인증 발급
- [ ] 빌링키 발급/정기결제 API 연동
- [ ] 환불·해지 정책 수립 및 약관 반영
- [ ] 전자세금계산서 자동발행 연동
